## 5. البناء والتثبيت عبر APK

من جذر المستودع:

```bash
cd apps/mobile/android
./gradlew :app:assembleDebug --no-daemon
```

ينتج الملف هنا:

```text
apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk
```

### التثبيت على جهاز Android عبر ADB

فعّل **Developer options** و **USB debugging** على الجهاز، ثم:

```bash
adb devices
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

أو من جذر المستودع:

```bash
adb install -r apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk
```

معرّف نسخة Debug هو:

```text
com.fuchsia.platform.debug
```

لإزالة النسخة السابقة:

```bash
adb uninstall com.fuchsia.platform.debug
```

للتشغيل من ADB:

```bash
adb shell monkey -p com.fuchsia.platform.debug 1
```

### التثبيت اليدوي

انسخ `app-debug.apk` إلى الهاتف، افتحه، واسمح بتثبيت التطبيقات من هذا المصدر عند طلب Android ذلك.


6. شغّل configuration باسم `app`.
7. اختر Variant:

## 9. ملاحظات مهمة قبل الإنتاج

دمج Google Maps SDK وPlaces وGeocoding لم يكتمل بعد في هذه النقطة. يوجد حاليًا اعتماد MapLibre في `app/build.gradle.kts`، لذلك لا ينبغي اعتبار نظام Google Maps جاهزًا للإنتاج أو الإعلان عن اكتماله.

عند بدء هذه المرحلة يجب:

- إزالة الاعتماد البديل بعد اكتمال دمج Google Maps.
- استخدام Google Maps SDK for Android.
- استخدام Places وGeocoding وفق مفاتيح مقيدة باسم الحزمة وSHA-1.
- حفظ المفتاح بطريقة آمنة وعدم رفعه إلى GitHub.
- اختبار صنعاء وعدن وتعز وإب والحديدة.

### API الإنتاجي والعناوين

ميزة العناوين تعتمد على API وتحتاج التحقق من نشر نسخة الخادم وترحيل قاعدة البيانات قبل اعتمادها على الإنتاج. يجب فحص:

```text

```

مع جلسة موثقة عند اختبار المسارات المحمية. لا تعتبر ميزة العناوين مكتملة إنتاجيًا إذا أعاد الخادم `404` أو لم تكن نسخة API وقاعدة البيانات متوافقتين.

### OTP_DEBUG

الإعداد الحالي في `app/build.gradle.kts` يحتوي على استثناء اختبار لإظهار OTP على الشاشة. قبل إصدار Production يجب مراجعة هذا الإعداد وإيقافه أو تغييره وفق سياسة المصادقة المعتمدة.

## 12. تدفق البداية بعد التثبيت

عند أول تشغيل بعد تثبيت التطبيق يظهر التدفق التالي:

1. شاشة ترحيبية أولى.
2. شاشة ترحيبية ثانية.
3. شاشة اختيار بعنوان «كيف تريد البدء؟» وتحتوي على:
   - «تسجيل الدخول».
   - «إنشاء حساب جديد».
   - «تصفح دون حساب».

زر «تخطي» من الشاشة الأولى لا يدخل إلى المتجر مباشرة؛ بل ينقل المستخدم إلى شاشة الاختيار نفسها، حتى يظل خيار تسجيل الدخول أو إنشاء الحساب واضحًا.

بعد اختيار «تصفح دون حساب» ينشئ التطبيق جلسة ضيف ويدخل إلى المتجر. أما تسجيل الدخول وإنشاء الحساب فينتقلان إلى شاشة المصادقة الحالية.

تم كذلك تكبير الشعار في رأس شاشة البداية والصفحة الرئيسية، وإظهار كلمة «بوتيك» بجانبه فقط وبنفس لون الشعار؛ لأن الشعار نفسه يحتوي على كلمة «فوشيا»:

```text
فوشيا [داخل الشعار]   بوتيك
```


## 13. شاشة تسجيل الدخول والإنشاء وتجربة الضيف

تم تطوير شاشة المصادقة لتصبح منظومة واحدة:

- رأس واضح يضم شعار «فوشيا» وكلمة «بوتيك» بجانبه بنفس لون الشعار.
- تبديل علوي مباشر بين «تسجيل الدخول» و«إنشاء حساب».
- زر الضيف متاح من وضعي الدخول والإنشاء.
- التحقق من البريد وكلمة المرور قبل إرسال الطلب.
- حالات تحميل تمنع التكرار أثناء الاتصال بالخادم.
- رسائل أخطاء واضحة داخل النموذج.
- إنشاء الحساب يرسل المستخدم إلى مسار OTP الحالي.

عند اختيار «التصفح دون حساب»:

1. يستدعي التطبيق `FuchsiaApi.guest()`.
2. يحفظ جلسة الضيف المشفرة داخل `SessionVault`.
3. يدخل المستخدم إلى المتجر دون بيانات حساب شخصية.
4. يظهر في رأس المتجر «أهلًا بك، ضيفنا» بدل اسم الضيف التقني.
5. يستطيع الضيف تصفح المنتجات والتصنيفات والبحث وفتح التفاصيل وإضافة المنتجات إلى السلة.
6. يمكن استخدام الحجز وCheckout وفق القيود التي يفرضها API.
7. تظهر مطالبة تسجيل الدخول عند الميزات التي تحتاج حسابًا دائمًا مثل حفظ المفضلة أو إدارة البيانات الشخصية، بحسب الشاشة والخدمة.

لإعادة اختبار التجربة بعد تثبيت سابق:

```bash
adb shell pm clear com.fuchsia.platform.debug
```

ثم شغّل التطبيق واختر:

```text
الشاشة الأولى → الشاشة الثانية → كيف تريد البدء؟ → تصفح دون حساب
```

## 15. إصلاح دخول الضيف من شاشة الترحيب

تم إصلاح مسار «تصفح دون حساب» من شاشة الترحيب. كان المسار يفتح الصفحة الرئيسية مباشرة دون استدعاء جلسة الضيف، ولذلك كانت السلة وCheckout تطلبان بدء التصفح مرة أخرى.

أصبح المسار الآن:

```text
شاشة الترحيب
→ تصفح دون حساب
→ FuchsiaApi.guest()
→ حفظ SessionVault
→ الصفحة الرئيسية
→ المنتجات والسلة وCheckout مباشرة
```

تظهر شاشة انتظار بعنوان «نجهّز لك التصفح دون حساب» أثناء إنشاء الجلسة، وتظهر شاشة إعادة محاولة واضحة عند فشل API. لا يتم اعتبار Onboarding مكتملًا إلا بعد نجاح إنشاء جلسة الضيف.

## 20. قائمة اختبار التسليم للمطور

### الوضع الليلي

1. فتح التطبيق.
2. الدخول إلى «حسابي» ثم «الإعدادات والمظهر».
3. اختيار «ليلي».
4. التحقق من الصفحات التالية:
   - الرئيسية.
   - التصنيفات.
   - تفاصيل المنتج.
   - السلة.
   - Checkout.
   - حسابي.
   - الإعدادات.
   - الطلبات.
   - العناوين.
   - حجز القاعات.
5. التأكد من أن النصوص الأساسية بيضاء وليست سوداء أو حمراء.
6. التأكد من أن الأيقونة والنص في «حجز قاعة أعراس» متناسقان.
7. التأكد من أن أيقونة ونص «حسابي» في الشريط السفلي متناسقان.
8. تجربة الوضع «حسب الجهاز» ثم «نهاري» للتأكد من عدم كسر ألوان الوضع الفاتح.

### التدفق التجاري الحالي

1. Onboarding.
2. تسجيل الدخول أو التصفح كضيف.
3. البحث عن منتج.
4. فتح تفاصيل المنتج.
5. تغيير الكمية.
6. إضافة للسلة.
7. متابعة الطلب من السلة.
8. Checkout.
9. العنوان والخريطة الحالية.
10. الطلبات والمفضلة والحساب.
11. حجز القاعة وتقويم التوفر.

## 21. نقطة البداية التالية المقترحة

بعد مراجعة هذه التحديثات، يبدأ التطوير التالي من مسار القاعات التجاري وليس من إعادة تصميم الواجهة:

1. إنشاء جداول مستقلة للقاعات وملاك القاعات.
2. إضافة حساب مالك القاعة ولوحة إدارة.
3. إضافة صور القاعة ومعلوماتها وموقعها.
4. إضافة أسعار أيام الأسبوع والمواسم.
5. إدارة التوفر والحجوزات من طرف المالك.
6. إضافة شروط الدفع والتأمين.
7. ربط المحافظ الإلكترونية اليمنية بطريقة آمنة وقابلة للتدقيق.
8. إضافة عمولة التطبيق البالغة 1000 ريال لكل حجز بعد تثبيت قواعد الأعمال.
9. إضافة حالات الحجز: مسودة، بانتظار الدفع، بانتظار التأكيد، مؤكد، ملغى، مسترد.
10. اختبار API الإنتاجي قبل تفعيل الدفع الحقيقي.

الوضع الحالي للقاعات هو **واجهة وAPI أولي فقط**، ولا ينبغي اعتباره نظام دفع أو حجز إنتاجيًا حتى تكتمل هذه المرحلة.
