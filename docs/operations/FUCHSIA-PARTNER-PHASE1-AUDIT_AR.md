# تدقيق تطبيق Android للشركاء — المرحلة الأولى

**تاريخ التدقيق:** 2026-10-16  
**الفرع المفحوص:** `feat/admin-phase2-deep-management`  
**المسار:** `apps/partner/android`  
**نطاق المرحلة:** فهم الحالة الحالية، حصر الوظائف والشاشات، مطابقة الـAPI، فحص المصادقة والحماية، وتحديد الفجوات قبل التطوير.

## الخلاصة التنفيذية

التطبيق الحالي ليس نموذجًا فارغًا؛ بل يحتوي على مساحة شريك متقدمة نسبيًا تشمل:

- تسجيل الدخول وتخزين جلسة مشفرة عبر Android Keystore.
- طلب اعتماد مالك الشريك.
- إدارة القاعات وحجوزاتها.
- التقويم الشهري والتوفر الأسبوعي والإغلاقات.
- إدارة منتجات الإيجار والصور والمخزون.
- حجوزات الإيجار وطلبات تغيير الموعد.
- فترات الصيانة.
- تقويم موحد للقاعات والإيجارات.
- إشعارات الشريك.

لكن التطبيق **غير جاهز لتجربة تشغيل حقيقية مع الخادم الحالي**؛ فالخادم المنشور على `https://fuchsia-x7dwxpzd.manus.space` أعاد `404` لمسارات الشريك التالية، بينما أعاد `/api/healthz` حالة `200`:

| المسار | النتيجة الحالية |
|---|---:|
| `/api/healthz` | `200` |
| `/api/venue-partner/me` | `404 Cannot GET` |
| `/api/vendor/stores` | `404 Cannot GET` |
| `/api/vendor/rental-bookings` | `404 Cannot GET` |
| `/api/notifications/partner` | `404 Cannot GET` |

هذا يعني أن الأولوية الأولى ليست إضافة شاشات جديدة، بل **توحيد نسخة الـAPI المنشورة مع الفرع الذي يحتوي مسارات الشريك، ثم اختبار العقد بين التطبيق والخادم على staging**.

## خريطة التطبيق الحالية

### الدخول والحساب

الملفات الرئيسية:

- `MainActivity.kt`
- `PartnerApi.kt`
- `PartnerSession.kt`

التدفق الحالي:

1. تسجيل الدخول عبر `POST /api/auth/login`.
2. حفظ `token` وبيانات المستخدم في `SharedPreferences` بعد تشفيرها بـ AES-GCM.
3. حفظ مفتاح التشفير داخل Android Keystore.
4. تحميل الملف عبر `GET /api/venue-partner/me`.
5. توجيه المستخدم حسب حالة الشريك: طلب اعتماد، انتظار، غير نشط، أو لوحة التحكم.

### المعاينة

يوجد وضع معاينة Debug ببيانات وهمية محلية. الكود يوضح للمستخدم أن:

- البيانات تجريبية.
- الإجراءات لا تُرسل للخادم.
- الصور لا تُرفع.
- المنتجات وقرارات الحجوزات لا تُحفظ.

هذه نقطة جيدة للاختبار البصري، لكنها لا تثبت صحة الربط التشغيلي.

## الفحص الأمني

### نقاط جيدة

- استخدام `Authorization: Bearer` لجميع الطلبات المحمية.
- عدم إرسال `storeId` أو `venueId` كبديل عن هوية المستخدم؛ الخادم يجب أن يتحقق من الملكية.
- استخدام `usesCleartextTraffic="false"`.
- عدم وجود WebView أو عناوين HTTP صريحة داخل التطبيق.
- تخزين الجلسة بتشفير AES-GCM ومفتاح Android Keystore.
- وجود مهلات اتصال وقراءة للشبكة.
- وجود وضع معاينة منفصل عن البيانات الحقيقية.

### نقاط تحتاج تطويرًا

1. **توحيد طبقة الشبكة:** يوجد تكرار لمنطق `HttpURLConnection` في `PartnerApi.kt` و`PartnerRentalApi.kt`.
2. **إدارة انتهاء الجلسة:** لا يوجد مسار موحد واضح لتحويل `401` إلى تسجيل خروج وإعادة توجيه المستخدم.
3. **منع التكرار:** عمليات الإنشاء والقرارات لا يظهر أنها تستخدم idempotency keys من جانب تطبيق الشريك.
4. **الرفع:** يتم تحميل الصورة كاملة إلى الذاكرة عبر `readBytes()`؛ الصور الكبيرة قد ترفع استهلاك الذاكرة.
5. **فتح الإيصال:** رابط الإيصال يُفتح خارجيًا؛ يجب التأكد أن الخادم لا يعيد رابطًا عامًا أو مكشوفًا، وأنه رابط مؤقت/مصرح به.
6. **النماذج:** الاعتماد على `JSONObject` يقلل أمان الأنواع ويجعل تغييرات عقد الـAPI قابلة للانكسار بصمت.
7. **الاختبارات:** لا توجد اختبارات Android واضحة لتدفقات الجلسة، parser، الحالات، أو عقود الـAPI.

## نتيجة البناء

تمت محاولة بناء:

```bash
ANDROID_HOME=/usr/lib/android-sdk \
ANDROID_SDK_ROOT=/usr/lib/android-sdk \
./gradlew :app:assembleDebug --no-daemon
```

النتيجة لم تصل إلى فحص كود Kotlin لأن بيئة الـSandbox تفتقد Android SDK، كما كانت تفتقد `javac` في البداية. تم تثبيت JDK 21 الكامل، لكن لا يوجد SDK في أي من المسارات القياسية المفحوصة. لذلك لا أصف البناء الحالي بأنه ناجح أو فاشل بسبب التطبيق نفسه؛ **البناء غير قابل للتنفيذ في البيئة الحالية قبل توفير Android SDK**.

## الأولويات المقترحة بعد التدقيق

### P0 — قبل أي اختبار حقيقي

1. نشر نسخة API التي تحتوي `venue-partner`, `vendor`, `notifications`, `uploads` على staging.
2. تجهيز migrations المطلوبة على staging فقط.
3. تشغيل اختبار عقد API من دون بيانات حساسة.
4. إنشاء حساب شريك وبيانات اختبار وربط متجر/قاعة به.
5. إعادة بناء Debug بعنوان staging وليس عنوان الإنتاج.

### P1 — أول تطوير فعلي داخل التطبيق

1. طبقة شبكة مشتركة مع معالجة موحدة لـ `401`, `403`, `404`, `409`, `429`.
2. اختبارات parser وعقد الطلبات الأساسية.
3. تحسين رفع الصور ليكون streaming أو مضغوطًا قبل الإرسال.
4. تحديث الحالة بعد كل قرار من الخادم بدل الاعتماد على إعادة تحميل عامة فقط.
5. إظهار حالة الاتصال وآخر وقت تحديث.
6. إضافة حماية من الضغط المكرر وidempotency للعمليات الحساسة.

### P2 — تحسينات المنتج

1. فصل الشاشات الكبيرة إلى ViewModels/مكونات مستقلة.
2. استبدال `JSONObject` بنماذج typed وserialization منظم.
3. إضافة بحث وفرز وتصفية للمنتجات والحجوزات.
4. إضافة إدارة ملف الشريك والمتجر والطاقم إن كانت ضمن نطاق المنتج.
5. إضافة اختبارات UI ولقطات للحالات العربية RTL.
6. إعداد إصدار Release موقع بعد نجاح staging، وليس قبل ذلك.

## قرار المرحلة الأولى

- **حالة التطبيق:** واجهة ووظائف كثيرة موجودة، وليست بحاجة إلى إعادة بناء من الصفر.
- **حالة الربط:** غير جاهز على الخادم المنشور الحالي بسبب `404` لمسارات الشريك.
- **حالة البناء:** لم يُتحقق منها في Sandbox لغياب Android SDK.
- **حالة المستودع:** لا توجد تغييرات كود تطبيق ناتجة عن هذا التدقيق؛ هذا الملف توثيق فقط.
- **الخطوة التالية الموصى بها:** تجهيز staging للـAPI وقاعدة البيانات، ثم تنفيذ اختبار تكاملي واحد كامل: تسجيل دخول الشريك → تحميل المتجر/القاعة → تنفيذ تغيير تجريبي → التحقق من ظهوره في لوحة التحكم وتطبيق العميل.
