# Fuchsia Boutique — تسليم المرحلة الثالثة للشركاء

**الحالة:** منفّذة في فرع التطوير `feat/android-expo-app`، مع نسخ Android Debug للمعاينة. لم تُنشر بعد على بيئة التشغيل الحية، ولا يُعد نجاح البناء اختبارًا لقاعدة بيانات الإنتاج.

## ملخص التنفيذ

تضيف المرحلة الثالثة إدارة توفر الإيجارات حسب التاريخ والكمية، طلبات تغيير الحجز، إشعارات داخلية للشريك، وتقويمًا شهريًا موحدًا يعرض حجوزات القاعات والإيجارات.

### حجز القاعات والإيجار

- الكوش والطاولات إيجار مباشر: زر المنتج «احجز الإيجار» يفتح اختيار التاريخ والمدة والكمية والتوصيل، ويفحص التوفر ثم ينشئ الحجز عبر `/api/rental-bookings` مباشرةً. لا يضاف المنتج إلى سلة المشتريات؛ API السلة يرفض عناصر `rental` ويزيل العناصر القديمة منها.
- للعميل: شاشة «طلباتي» تعرض إجراء طلب **إلغاء** أو **تغيير تاريخ** عند وجود إيجار نشط في حالات انتظار التأكيد أو المؤكد أو قيد التجهيز. لا تظهر هذه الإجراءات لطلبات القاعات أو مشتريات السلة.
- نقل الموعد أو الإلغاء **طلب يحتاج قرار المتجر**؛ يبقى التاريخ الأصلي والحجز كما هما حتى قبول الطلب. لا ينفذ النظام استردادًا أو تعديلًا ماليًا تلقائيًا.
- للقاعة: **لا يقدّم العميل أو الشريك أو لوحة الإدارة الحالية طلب إلغاء/تحويلًا إلى `cancelled`**. نقطة طلب العميل تردّ `403`، كما تُرفض حالة `cancelled` في واجهتي الشريك والإدارة برسالة توضح أن الشروط ستُعرّف لاحقًا من لوحة التحكم. لا يوجد تغيير تاريخ القاعات.
- تخضع طلبات التغيير لحالة `pending` واحدة لكل حجز، وتُرفض الطلبات المكررة أو التي جرى البت فيها. تسجل قرارات الشريك في سجل الأحداث ويُخطر العميل.
- عند قبول نقل تاريخ الإيجار، يعاد فحص المخزون على التواريخ المطلوبة داخل المعاملة، بعد قفل سجل المنتج، مع استبعاد الحجز الأصلي من الإشغال. لا يغيّر القرار الأسعار أو الدفعات آليًا.

### توافر الإيجارات والصيانة

- تحسب الإتاحة لكل يوم من أيام الإيجار على أساس الكمية، والحجوزات المتداخلة، وكتل الصيانة، ومهلة التجهيز. لا يكفي أن يكون المنتج منشورًا أو أن يوجد مخزون إجمالي.
- أضيف حقل «مهلة التجهيز بعد الحجز» لمنتج الإيجار (0–14 يومًا)، بالإضافة إلى واجهة المتجر لتسجيل فترة صيانة للمنتج والكمية/السبب وحذفها. الخادم يرفض إغلاق كمية تتعارض مع حجوزات أو صيانة قائمة.
- تدعم فترات الصيانة تواريخ مستقبلية خلال 180 يومًا وبحد أقصى 90 يومًا للفترة الواحدة.

### التقويم الموحد للشريك

يظهر التبويب عند امتلاك الشريك قاعة ومتجر إيجار معًا، ويجمع حجوزات القاعات والإيجارات على الشبكة الشهرية نفسها، مع أسماء أيام الأسبوع واليوم الحالي، ومؤشرات منفصلة للقاعة والإيجار، وتفاصيل الحجوزات التي تغطي اليوم المحدد. يعتمد العرض على تواريخ الإيجار المحفوظة الفعلية، ويعرض حالة الانتظار/التأكيد.

## واجهات API المضافة أو المستخدمة

جميع المسارات تحت `/api`:

| المسار | الاستخدام |
|---|---|
| `POST /venue-bookings/:id/cancellation-requests` | موقوف مؤقتًا؛ يتطلب مصادقة ثم يردّ `403` إلى أن تُحدد سياسة الإلغاء في لوحة التحكم. |
| `POST /rental-bookings/:id/change-requests` | إرسال طلب `cancel` أو `reschedule` للإيجار من العميل. التاريخ الجديد بصيغة `YYYY-MM-DD` عند طلب النقل. |
| `GET /vendor/rental-bookings?storeId=…` | تحميل حجوزات المتجر، وتشمل `changeRequests` المعلّقة لكل طلب. |
| `PATCH /vendor/rental-bookings/:id/change-requests/:requestId` | قرار المتجر (`approve`/`reject`) مع سبب رفض مطلوب. يعيد فحص المخزون قبل قبول نقل الموعد. |
| `GET /vendor/rental-maintenance?storeId=…&month=YYYY-MM` | عرض كتل صيانة منتجات المتجر. |
| `POST /vendor/rental-maintenance` | إضافة إغلاق صيانة مع المنتج والفترة والكمية والسبب. |
| `DELETE /vendor/rental-maintenance/:id` | حذف فترة صيانة يملكها المتجر. |

تتطلب واجهات الشريك جلسة مصادقة وصلاحية المالك؛ ويتحقق الخادم من ملكية المتجر/القاعة. تُسجل طلبات الإيجار وقراراتها في `booking_change_requests` وسجل أحداث الحجوزات. تغيير حالة القاعة إلى `cancelled` مرفوض من واجهة الشريك حتى إضافة قواعد الإلغاء.

- `artifacts/api-server/src/lib/migrations.ts`: ترحيل إضافي قابل لإعادة التشغيل بالمعرّف `20261009_partner_operations_phase3_v1`، يضيف عمود مهلة التجهيز وينشئ الجداول والفهارس باستخدام `IF NOT EXISTS` ويفحص العمود قبل إضافته.

**تنبيه تشغيل:** فحص الشيفرة لا يثبت تطبيق الترحيل على قاعدة البيانات الحية. يجب نشر نسخة API على بيئة staging، ثم مراجعة سجل تشغيل `runMigrations()` والتحقق من أسماء الأعمدة والجداول قبل اختبار تدفق بيانات حقيقي.

## التطبيقات

- **Customer Android:** `apps/mobile/android` — مسار إيجار مباشر للكوش والطاولات وطلبات الإلغاء/نقل موعد الإيجار ضمن شاشة الطلبات، مع إبقاء الحجز القائم حتى قرار المتجر. القاعات لا تعرض إجراء إلغاء.
- **Partner Android:** `apps/partner/android` — تبويب التقويم الموحد، طلبات الإيجار وقراراتها، إدارة الصيانة، وحقل مهلة التجهيز في محرر المنتجات.
- البيانات الوهمية في وضع المعاينة تظل محلية ولا تنشئ حجوزات أو قرارات حقيقية.

## التحقق الذي أُجري

- `pnpm run typecheck:libs` — ناجح.
- `pnpm --dir artifacts/api-server typecheck` — ناجح.
- تطبيق العميل: `:app:compileDebugKotlin` — ناجح.
- تطبيق الشريك: `:app:assembleDebug` — ناجح بعد تصحيح نطاق Modifier.
- `:app:assembleDebug` للعميل والشريك — ناجحان؛ النسختان Debug للمعاينة فقط.

## ما بقي قبل staging/النشر

1. نشر migration وAPI على قاعدة staging فقط أولًا، وفحص endpoint غير موجود الذي كان يعيد `404` في البيئة الحالية.
2. اختبار العميل → إشعار الشريك → قرار الشريك → إشعار العميل على بيانات staging، مع اختبار تعارض كمية وحجز متداخل وصيانة ومهلة تجهيز.
3. مراجعة سجل الأحداث والإشعارات، والتحقق من حالات الحجز والدفعات يدويًا؛ لا توجد معالجة استرداد أو تعديل مالي آلي.
4. بعد نجاح staging فقط، ترتيب النشر على البيئة الحية باتفاق منفصل. لم يتم هنا تغيير إعدادات استضافة أو كتابة بيانات على قاعدة حية.

## البناء المحلي للمعاينة

من مجلد التطبيق:

```bash
ANDROID_HOME=/usr/lib/android-sdk ANDROID_SDK_ROOT=/usr/lib/android-sdk ./gradlew :app:assembleDebug
```

ملفات Debug الناتجة تحت `app/build/outputs/apk/debug/app-debug.apk`. هذه ملفات معاينة وليست إصدار إنتاج أو APK موقعًا للنشر العام.
